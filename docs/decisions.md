# Architecture Decision Records

Short records of decisions that shaped the system: the context, what was decided, and what it costs.

## ADR-001: Prisma 6 on SQLite

- **Context:** The brief suggests SQLite. We want typed queries, migrations and an easy path to Postgres. At the time of writing, npm's `latest` tag for Prisma pointed to an 8.0 release candidate.
- **Decision:** Use **Prisma 6.19** (the latest stable major we know well) with SQLite. Raw SQL (`$queryRaw`) is allowed only inside repositories, for aggregations Prisma cannot express (for example medians).
- **Consequences:** Zero-ops database in a single file. Moving to Postgres is a `provider` change plus a migration. SQLite has a single writer, which is fine for an HR team and noted as a scale limit.

## ADR-002: Salaries as whole-unit integers

- **Context:** The first design stored money in minor units (cents or paise). Prisma's `Int` is 32-bit (max ≈ 2.1 billion), so a salary in paise would overflow above ₹21M (~$250k). A senior Indian executive could realistically exceed that.
- **Decision:** Store the **annual salary as an integer in whole currency units** plus an ISO 4217 currency code. Annual salaries are agreed in round numbers, so cents carry no information here.
- **Consequences:** No floating-point error and no overflow risk (the limit is 2.1 billion of any currency). If sub-unit amounts are ever needed (for example hourly rates), revisit with `BigInt` or `Decimal`.

## ADR-003: Current salary on the employee row, plus append-only revisions

- **Context:** List views and every aggregation need the current salary. History is only needed on the detail page and for "recent changes".
- **Decision:** `Employee.salary` holds the current value. `SalaryRevision` is append-only and written in the **same transaction** as any salary change. The seed generates an initial revision for every employee and 0–2 raises.
- **Consequences:** Hot reads need no join. The cost is a small amount of denormalisation, kept consistent by a single service method and covered by tests.

## ADR-004: Deterministic, realistic seed data

- **Context:** The data needs to be big enough to prove behaviour at 10k scale and realistic enough to make the insights meaningful. Tests need stable data.
- **Decision:** A pure `generateEmployees({ count, seed, referenceDate })` function. It weights the country and department mix, gives senior titles higher US base pay, applies a per-country pay factor and converts to local currency at static FX rates, and uses locale-specific names. It never reads the real clock. The seed script re-creates the data in one transaction.
- **Consequences:** The same data on every machine and in every run. Seeding 10k employees and ~16k revisions takes about 2 s.

## ADR-005: Offset pagination, substring search, whitelisted sorting

- **Context:** The HR manager browses, searches and filters 10k employees. The brief evaluates how this is handled at scale.
- **Decision:**
  - All filtering, searching, sorting and paging happens **in the database**. The client never downloads the full list.
  - **Offset pagination** (`page`, `pageSize` ≤ 100) with a secondary sort on `id`, so pages stay stable when sort values tie. It returns `total` and `totalPages` so the UI can jump to any page.
  - **Search** is a case-insensitive substring match (`LIKE %term%`) on name, email and employee code. Filters (country, department, job title, status) are exact matches combined with AND.
  - `sortBy` is a **whitelist**, so clients cannot sort on arbitrary or unindexed columns.
- **Consequences:** Measured on 10k rows: list and filter queries take 9–25 ms and a warm search ~22 ms. A leading-wildcard `LIKE` cannot use an index, which is fine here but grows linearly. The upgrade paths are FTS5 for search and keyset pagination for very deep pages. SQLite's `LIKE` only ignores case for ASCII, so "Ö" will not match "ö". This is acceptable for v1 and FTS5 fixes it.

## ADR-006: Salary, country and status each have their own workflow

- **Context:** A generic `PATCH` that can change anything would let the salary change without a revision record, or move someone to another country while leaving their salary in the old currency.
- **Decision:** `PATCH /employees/:id` accepts only descriptive fields (name, email, title, department, employment type, hire date) and **rejects unknown keys** (a strict schema). Salary changes go through `POST /employees/:id/salary` (Phase 4), which always records a revision. Termination is `DELETE`, which is a soft delete. Relocation to another country is out of scope for v1.
- **Consequences:** The audit trail cannot be bypassed. Employee codes (`EMP#####`) are generated by the server from the row id inside the create transaction, so they are unique without a separate sequence table.

## ADR-007: Salary change rules

- **Context:** A salary change is the most sensitive write in the system. History must stay trustworthy, and two HR users must not silently overwrite each other.
- **Decision:** `POST /employees/:id/salary` with `{ salary, effectiveDate, reason }`. The salary update and its revision row are written in **one transaction**. The service enforces these rules (422 `BUSINESS_RULE_VIOLATION`):
  - The employee must be **active**.
  - The new salary must **differ** from the current one. Decreases are allowed, for example a move to part-time.
  - The effective date must be **on or after** the current salary's effective date, so history stays in order. A same-day correction is allowed.
  - The effective date **cannot be in the future**. Scheduled changes would need a pending state and a job to apply them, which is out of scope for v1. "Today" comes from an injected clock, so tests are deterministic.
  - **Optimistic concurrency:** the update only matches if the salary is still what the service read. Otherwise the request fails with 409 and the user reloads.
- **Not enforced in the API:** an upper bound on the size of a change. A manual test accepted £55,400 → £999,999, almost certainly a typo, but large legitimate changes exist. The UI will ask for confirmation when a change exceeds ±30% instead of blocking it.
- **Consequences:** Every salary change is explained (it has a reason), ordered, and attributable to a date. All rules are unit-tested with a fake repository, and mutation-checked: removing any rule makes a test fail.
